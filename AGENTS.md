# Config repo

Personal dotfiles/config repo, installed by symlinking files into `$HOME`.

## Live-edit warning

`install.sh` symlinks most top-level files and directories into `$HOME`, so edits in this repo take effect immediately on the installed system.

The reverse also holds: `~/.claude/CLAUDE.md` is `INSTALL-AGENTS.md`, and `~/.pi/agent/skills`, `~/.pi/agent/extensions` and the other symlinked `~/.pi/agent` entries point into `pi/`. Editing them through their `$HOME` paths is a change to this repository.

## install.sh

Symlinks configs into `$HOME`, sets global git config, and syncs vim (vim-plug) and nvim (lazy.nvim) plugins. The repo must live at `~/config`. Do NOT run it — it is only run manually.

## Binaries

`binaries/download.sh` pins tool versions via the `*_VERSION` variables at the top, verifies checksums, and extracts binaries into `binaries/<OS>/<arch>/`. Those directories are gitignored: the binaries are not committed, and `install.sh` runs the script whenever one of the expected tools is missing for the host platform.

By default the script only downloads the host platform; `--all` gets all three. Downloads happen in a scratch directory, so nothing is left behind in `binaries/` on failure. To bump a version: edit the `*_VERSION` variable, and for bat, jj and tuicr also the pinned digests in `download_platform` (they publish no checksum assets), then re-run the script.

## pi extensions

`pi/extensions/` is symlinked to `~/.pi/agent/extensions`, so every `*.ts` there is loaded globally. Nothing hot-reloads: pi has to be restarted before a change takes effect, and there is no typecheck for these files.

Discovery only picks up `*.ts` and `*/index.ts`, so `pi/extensions/lib/` holds shared modules without being loaded as extensions — never add `lib/index.ts`.

`pi/extensions/claude-bridge/` is a fork of the MIT-licensed `@vanillagreen/pi-claude-bridge` (the `pi-claude` provider that routes turns through Claude Code via the Claude Agent SDK). It keeps the upstream layout (`src/`, `tests/`) behind a thin `index.ts`; its `README.md` lists the differences from upstream and `LICENSE` carries the upstream copyright. It has its own `package.json`; `node_modules/` is gitignored and `install.sh` runs `npm ci` there when it is missing. `npm test` and `npm run typecheck` run offline in that directory. Pi aliases `@earendil-works/*` imports to its own copies, so the pi packages in `devDependencies` only serve tests and typechecking.

`pi/extensions/i-have-adhd/` is a fork of the MIT-licensed `ayghri/i-have-adhd` (an output-style mode toggled with `/i-have-adhd`). The ruleset is `pi/skills/i-have-adhd/SKILL.md`, which the extension reads on load, so edit the rules there. Whether it starts on by default is `iHaveAdhd.alwaysOn` in `pi/settings.json`. Both directories carry the upstream `LICENSE`; the extension's `README.md` has the upstream commit and the differences. It is not listed under `packages` in `settings.json` anymore; re-adding it would register the command twice.

`pi/extensions/crit.ts` wraps the `crit` CLI (`crit_review`, `crit_comments`, `crit_comment`, `crit_status`). Story mode is authored in-session: `crit_story_prepare` runs `crit story --guide` and `crit story --prep` (prep file in the session scratch directory), and `crit_review` with a `story` object ingests it via `crit story --story-file --refresh` before the usual wait for Finish Review. `--refresh` is deliberate: without it crit keeps an existing story and skips the ingest. Bare `crit story` (the `agent_cmd` path) is not used.

The file tools (`read`, `write`, `edit`, `ls`, `find`, `grep`, `delete`) go through the path-permission engine in `pi/extensions/lib/path-permissions.ts`: the repository and the memory, skill, plan and crit directories are allowed by default (plus the session scratch directory returned by `temp_dir`, which subagents inherit from their parent through `PI_SESSION_TEMP_DIR`), other paths prompt, and plan mode and explore mode make the repository read-only (except `.jj/working_copy/working_copy.lock` and `.jj/repo/git_import_export.lock`, which even read-only jj commands take). Rules are globs, persisted in `~/.pi/agent/path-permissions.json` (always) and the session (session); manage them with `/plan grants`, `/plan allow <glob>` and `/plan deny <glob>`. `read`, `write`, and `edit` wrap Pi's stock implementations while remaining subject to the path-permission engine.

Explore mode (`/explore`, `--explore`, `pi/extensions/explore-mode.ts`) is plan mode without the planning tools, meant for read-only codebase exploration. `exploreMode.alwaysOn: true` in `pi/settings.json` starts every new session (launch or `/new`) in explore mode; resumed sessions keep their recorded mode, the flags still win, and sessions without a UI (subagent children, `pi -p`) and the fresh plan-handoff session ignore it. It is mutually exclusive with plan mode (toggling one leaves the other). It keeps its own memory: tool decisions in `~/.pi/agent/explore-mode.json` and the `explore-mode` session entry, path rules in `~/.pi/agent/explore-path-permissions.json` and the `explore-path-permissions` entry, managed with `/explore grants` and `/explore allow|deny <glob>`. Unlike plan mode, it leaves the tuicr tools ungated. While exploring, the shared path-rule store is ignored; subagents enforce the store of the mode they were dispatched from. The mode message also tells the LLM to pass `--ignore-working-copy` to every jj command, because jj cannot snapshot a read-only working copy; the cost is that `@` can be stale until something snapshots. Both modes run on the shared engine in `pi/extensions/lib/restricted-mode.ts` (found through the runtime's event bus, so the two extensions load in any order); the mode reaches the model as an appended hidden `agent-mode-state` message, so toggling never invalidates the prompt cache.

`pi/extensions/sandbox/` overrides the built-in `bash` with one that runs every command inside `@anthropic-ai/sandbox-runtime` (pinned exactly: research preview, config format may change): Seatbelt on macOS, bubblewrap + seccomp on Linux (`sudo pacman -S bubblewrap socat ripgrep`; without them bash fails closed with an install hint; Ubuntu additionally needs `kernel.apparmor_restrict_unprivileged_userns=0` and the `bwrap-userns-restrict` AppArmor profile unloaded, because that profile strips capabilities from bwrap's children and so breaks srt's `apply-seccomp` helper). The per-command filesystem policy is derived from the path-permission engine (`currentPolicy()`), so the OS enforces the same read/write rules as the file tools. `$HOME` is deny-read except the engine's read-allowed trees, a toolchain list and the `@anthropic-ai/sandbox-runtime` package itself (srt runs its vendored seccomp helper inside the sandbox, so the package must stay readable wherever `node_modules/` lives), and a built-in secret list (`.ssh`, `.aws`, `.gnupg`, pi auth files, ...) is denied for reads and writes even when a broad grant exists. After a failed command, denied paths are prompted once each: "in session" and "always" answers are recorded as ordinary path rules and the agent has to rerun, while "Allow once" makes the sandbox rerun the command right away with that grant added for the rerun only (both runs' output lands in one tool result), as long as no other path of that run stayed blocked. Violations come from the extension's own collector (`src/violation-collector.ts`), not srt's store: on macOS it runs its own `log stream`, because srt's monitor keeps only the first violation of each output chunk, and on Linux it copies every entry from srt's store before its 100-entry ring evicts it. On Linux, read-denied paths are masked with a tmpfs, so a denied read fails with ENOENT and produces no violation record or prompt (srt 0.0.77's observer only reports write-intent syscalls); grant read access through the file tools instead. A command that exits 0 despite sandbox denials (e.g. `cat secret 2>/dev/null || true`) is reported in a `<sandbox_violations>` block but not prompted and not rerun. Only Linux reports a denied write as discarded (its tmpfs swallowed it); macOS refuses the write and reports it as denied. Environment variables whose names look like credentials (matching `api key`, `access key`, `secret`, `token`, `password`, `credential` or `private key`, case-insensitive) are masked inside the sandbox: the process sees a sentinel, and the proxy substitutes the real value on egress to allowed domains. A tool that needs the real value locally (not through an allowed domain) will not find it; run that command with `unsandboxed: true`. Network is deny-all except the allowlist in `~/.pi/agent/sandbox.json` (optional; defaults cover GitHub, npm, crates.io and PyPI) and interactive host prompts. Subagent children get no network at all: their sandbox ignores the allowlist and session grants, denies every host and disallows unix sockets and local binding. `PI_SANDBOX=0` skips the extension and restores stock bash; that also happens silently if the extension fails to load (e.g. `node_modules/` missing), so restart pi and check that the bash tool description mentions the sandbox. Plan and explore mode leave bash ungated while the sandbox is active, since the sandbox makes the repository read-only. Subagent children of a plan- or explore-mode session get bash on the same condition: the parent admits it only while its sandbox is active, the child blocks it when its own sandbox did not load, and the child's system prompt carries the `--ignore-working-copy` note because it gets no mode message. The sandbox resets srt on `session_shutdown`: its proxy servers and the macOS `log stream` monitor otherwise keep the event loop alive, and a `pi -p` subagent child that ran bash would never exit. As a safety net, the subagent tool terminates a child that has not exited 10 s after its final `agent_end` (`subagent/exit-watchdog.ts`) and appends a note to its otherwise complete output. `bash` also takes `unsandboxed: true` for commands the sandbox itself breaks: the user confirms each one in a prompt whose preselected answer is allow, or deny in plan mode ("in session" answers hold until pi restarts, they are not persisted); subagents are refused outright, and the call line is marked `unsandboxed $`.

The path engine also has a protected write layer: `pi/extensions/**`, `pi/skills/**` (through their `~/.pi/agent/...` symlinks), the global skill roots, `~/.pi/agent/*.json`, `install/`, `bin/` and `npm/` prompt for writes instead of being default-allowed, for the file tools and the sandbox alike. An explicit session or always grant still works (beware: a grant of a parent such as the home directory covers them); the grant prompt warns when the granted selector also covers protected paths, since such a grant disarms the layer.

Inside the repository's `.git` and `.jj`, sandboxed writes are limited to what git and jj need to run normally (`pi/extensions/sandbox/src/vcs-policy.ts`; the allowlist comes from the git and jj command batteries in the sandbox integration tests, and a missing entry shows up as a `<sandbox_violations>` report). The layout is scanned per command, since git and jj create and remove entries all the time. macOS replaces the repository write allow with "every top-level name except `.git` and `.jj`" (generated globs, both cases of the letters excluded) plus that allowlist; this also applies when the repository root itself is granted. Linux keeps the repository writable, because srt cannot express "deny `.git`, re-allow `.git/objects`" and creating a file needs a writable parent, and denies per command every existing non-allowlisted entry plus a list of dangerous names that do not exist yet. Linux gaps: `.git/commondir` (an empty placeholder file breaks git), and `.jj/repo/config.toml` and `.jj/workspace-config.toml` in repos without config ids (the sandbox warns once; `jj config path --repo` and `jj config path --workspace` create the ids). On macOS, top-level repository names that start with a character outside `[A-Za-z0-9_@,=~#%!&-]` (after an optional `.`) are not writable from bash. `git remote add` and `jj git remote add` still need `unsandboxed: true`, because `.git/config` stays denied. `git stash` reports one denied `.git` unlink, which git ignores. On macOS a jj checkout that deletes a top-level file tries to remove the repository root itself, which Seatbelt denies; that unlink is dropped before reporting and prompting. git-lfs may write `.git/lfs`, but a sandboxed `git lfs pull` can still fail on network or credentials. `.git/objects/**` stays writable as a whole, including `objects/info/alternates`, which only adds object sources. A directory without `.git` or `.jj` keeps the plain repository allow, so `git init` works there.

Sandbox limitations (each a candidate for `unsandboxed: true`): programs that ignore proxy environment variables have no network, and ssh git remotes do not work (use https); no listening sockets unless `network.allowLocalBinding` is set in `sandbox.json` (dev servers need it); on macOS the system resolver may still answer DNS lookups initiated inside the sandbox (socket-based filtering cannot see them) while the outbound sockets themselves are blocked except the proxy; on Linux glob write allows are dropped and glob write denies widen to their base directory; `git remote add` and `git config` inside the repository fail because srt protects `.git/config` and `.git/hooks`; every other dotfile in `~/config` is still default-allowed for writes.

`pi/extensions/cache-debug/` is always on (`PI_CACHE_DEBUG=0` turns it off) and is the first place to look when a prompt-cache miss needs explaining. It appends one JSON line per provider request to `~/.pi/agent/cache-debug/<session-id>.jsonl`: a fingerprint of the payload (a hash and size per top-level key and per array element such as each message, never content; `cache_control` markers are ignored), the response status and headers (cookies and credentials dropped), and the usage of the matching assistant message. Files untouched for 30 days are pruned at session start, and each is capped at 50 MiB. Read it with `/cache-debug [--all] [session-id]` in pi or `node pi/extensions/cache-debug/report.ts [--all] [<session-id>|<file>]`. Every miss is classified as `prefix-changed` (pi sent different content: the report names the first differing payload element and estimates its token offset), `provider-miss` (the previous payload is an exact prefix, so the miss happened on the provider's side; idle gaps over 5 minutes hint at TTL expiry) or `no-payload`. Refreshes from pi's cache warming (`cacheWarming`, `"idle"` by default since 1.5.1) are tagged through the `cache_warming_decision` event (`purpose` `"cache-warm"` on the record), reported as `cache-warm` and skipped as the comparison baseline; idle time still counts from them. Untagged refreshes in older logs show as `no-usage`. The payload is fingerprinted as `before_provider_request` sees it: the `pi-claude` bridge never calls `onPayload` and only logs usage, `before_provider_request` handlers that run after this extension are not reflected, and request headers (such as Mistral's `x-affinity`, set inside the provider) are not visible. The sandbox denies reads under `$HOME`, so agents need a read grant for `~/.pi/agent/cache-debug` to run the CLI.

`pi/extensions/default-model.ts` covers a gap in pi: when the `defaultProvider`/`defaultModel` model is missing or has no auth at startup, pi silently picks the first available model. On `session_start` (`startup` or `new`, with a UI, no conversation yet, no `--model`/`--models`, not a plan handoff) it compares the active model with the default. It refreshes the registry, switches to the default with `pi.setModel` if that now works (extension providers like `pi-claude` can register late), and warns in every case. The pure parts live in `lib/default-model.ts`.

`pi/extensions/foreign-thinking/` makes Pi 1.3.0's cross-model thinking handling configurable (Pi now drops thinking blocks from other models; 1.2 sent them as plain text). Its `context` handler rewrites assistant messages from another `provider`/`api`/`model` before the provider's `transformMessages()` sees them: `drop` removes their thinking, `text` (the default) replaces readable thinking with a `<prior_model_reasoning model="...">` text block, and `keep` gives the message the target model's identity so its thinking stays a thinking block. `keep` only applies when both sides use the same API (`claude-bridge` counts as `anthropic-messages`) and otherwise falls back to `text`; encrypted and empty thinking is always removed. Rules live under `foreignThinking` in `pi/settings.json` (`default`, plus `rules` with optional `from`/`to` globs over `provider/model`, where `*` also matches `/`; first match wins), read on `session_start`. `/foreign-thinking` shows them, `/foreign-thinking drop|text|keep` overrides every rule for the session and `reset` clears that. The `pi-claude` bridge is never a target: it has its own converter. The pure parts live in `policy.ts`.

`pi/extensions/sidebar/` draws a non-capturing overlay box in the top-right corner, made of sections (`SidebarSection` in `section.ts`). A new section is a module with a `create...Section(pi, changed)` factory, added to the `sections` array in `index.ts`. The only section so far lists the skills loaded on the current branch. Detection covers a successful `read` of a skill's `SKILL.md` (matched by realpath, so calls from codemode and the `pi-claude` bridge count too) and `/skill:name`; reads through bash are not detected. Each load is recorded as a `loaded-skill` custom session entry, so the list survives resume, fork, `/tree` and compaction. The box is hidden while every section is empty and on terminals narrower than 100 columns. Its width follows the widest row on every render, up to a third of the terminal width; this relies on pi-tui reading the overlay options object on every frame (a `width` getter in `index.ts`). The panel is shown with `tui.showOverlay` from inside a `ui.custom` factory that calls `done()` before returning: pi counts an open `ui.custom` call as a pending prompt and emits no `ui_prompt_start` for prompts nested in it, so an overlay held open through `ui.custom` silences `notify-ask.ts`. `/sidebar [on|off]` toggles it per session (`sidebar-visibility` entry); `sidebar.enabled` in `pi/settings.json` is the persistent default, and a missing key means on. `panel.ts` takes pi-tui's width helpers as an injected `TextMeasure` and the pure modules avoid enums and parameter properties, because CI's package-less `node --test` has neither pi-tui nor type transforms.

`submit_plan` and `crit_review` (when given a plan file inside the plans directory) commit the plan file into a repository in its plans directory (`~/.pi/agent/plans/<cwd-slug>/`), creating a colocated jj repository (or a git one when jj is missing) on first use. Commit messages are `Submit plan: <name>` and `Review plan: <name>`.

## pi skills

`pi/skills/` is symlinked to `~/.pi/agent/skills`, pi's global skill root. Each skill is `pi/skills/<name>/SKILL.md`. Skills meant for Claude Code as well go in `<name>-skill/` at the top level and are linked into `~/.claude/skills/` instead (see `tuicr-skill`). A skill for both lives in `pi/skills/<name>/` and `install.sh` links that directory into `~/.claude/skills/`; add its name to the `for skill in ...` loop there (see `rust-style`).

## pi themes

`pi/themes/` is symlinked to `~/.pi/agent/themes`, pi's global theme directory; pi loads every `*.json` there, and the active theme hot-reloads from it. `gruvbox-dark.json` (the `theme` in `settings.json`) is inlined from the MIT-licensed `@firstpick/pi-themes-bundle`; `pi/themes/README.md` lists the source and the differences, and `LICENSE` carries the upstream copyright. Validate theme files against `schemas/theme.schema.json` of the installed pi package.

## pi packages

`pi/npm/` holds `package.json` and `package-lock.json` for the npm packages in `settings.json`. `install.sh` symlinks both into `~/.pi/agent/npm` (pi's npm install root, whose own `.gitignore` ignores everything else) and runs `npm ci` there when `node_modules` is missing. `pi update --extensions` runs `npm install <name>@latest` there, which rewrites the repo files through the symlinks (npm writes through them, verified), so review and commit the diff after each update. Git packages have no lockfile: their commit is only recorded in the checkout under `~/.pi/agent/git/`.

## CI

`.github/workflows/` has six workflows with 8 independent jobs in total. GitHub's `paths:` filter works per workflow, so jobs that share inputs live in one workflow, each with a `push` (to `main`) and `pull_request` `paths:` filter (shared through a YAML anchor) that always includes the workflow's own file. `workflow_dispatch` and `schedule` ignore `paths:` and always run every job. `nvim`, `vim`, `extensions` and `binaries` also run weekly, to catch upstream breakage that a push wouldn't (`stable` nvim, vim-plug plugins, which have no lockfile, `latest` node, dead release URLs); `shellcheck` and `actionlint` don't, since their tools are pinned.

Known gap: the `shellcheck` paths cover `.sh` files plus the extensionless shell files by name (`.ansi-colors`, `.shellrc-common`, `.git_template/hooks/`); a new extensionless shell script elsewhere won't trigger it on its own PR, so add its path to `shellcheck.yml`.

`shellcheck.yml` (paths: shell files and `.github/scripts/shellcheck.sh`), `actionlint.yml` (paths: `.github/workflows/**`), `nvim.yml` (paths: `nvim/**`, `nvim-check.lua`), `vim.yml` (paths: `.vimrc`, `.vim/**`), `extensions.yml` (paths: `pi/extensions/**`, because `sandbox` imports from `pi/extensions/lib/`) and `binaries.yml` (paths: `binaries/download.sh`, `tuicr-skill/**`):

- **shellcheck**: lints shell scripts. `.github/scripts/shellcheck.sh` auto-discovers every tracked file with a shell shebang or `.sh` suffix and runs the same way locally.
- **actionlint**: lints the workflow files.
- **stylua**: checks formatting of `nvim/`.
- **node**: `npm ci` + `npm test` + `npm run typecheck` in every `pi/extensions/*/` directory that has a `package.json` (discovered automatically, so new packages need no workflow change but must define both scripts), plus `node --test pi/extensions/*/*.test.ts` for the package-less directories (`lib`, `subagent`, `cache-debug`, `foreign-thinking`, `sidebar`; the `lib` tests need `fd` on `PATH`). Matrixed on the `engines` floor (22.19.0) and `latest`.
- **nvim**: installs plugins from `nvim/lazy-lock.json` via `Lazy! restore`, then runs `.github/scripts/nvim-check.lua` headless, which force-loads every plugin and fails on any config error. Matrixed on `v0.12.0` (the floor, since `nvim-treesitter` on `main` requires it) and `stable`. `nvim-check.lua` runs the same way locally: `nvim --headless --cmd "luafile .github/scripts/nvim-check.lua"`.
- **vim**: installs plugins with vim-plug and checks for startup errors. vim-plug has no lockfile, so this always tests upstream HEAD — the weekly run is what surfaces breakage here.
- **downloads**: runs `binaries/download.sh` and smoke-tests every binary, natively on all three supported platforms (`ubuntu-26.04`, `ubuntu-26.04-arm`, `macos-26`).
- **sandbox**: runs `npm run test:int` in `pi/extensions/sandbox/` natively on `ubuntu-26.04` (with bubblewrap installed, the AppArmor userns sysctl lifted and Ubuntu's `bwrap-userns-restrict` profile unloaded) and `macos-26`; it drives the real sandbox, unlike the unit tests in the node job.

All actions are pinned to version tags; Dependabot (`.github/dependabot.yml`) keeps them current.

## Vendored code
