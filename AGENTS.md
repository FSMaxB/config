# Config repo

Personal dotfiles/config repo, installed by symlinking files into `$HOME`.

## Live-edit warning

`install.sh` symlinks most top-level files and directories into `$HOME`, so edits in this repo take effect immediately on the installed system.

The reverse also holds: `~/.claude/CLAUDE.md` is `INSTALL-AGENTS.md`, and `~/.pi/agent/skills`, `~/.pi/agent/extensions` and the other symlinked `~/.pi/agent` entries point into `pi/`. Editing them through their `$HOME` paths is a change to this repository.

## install.sh

Symlinks configs into `$HOME`, sets global git config, installs vim plugins (vim-plug) and restores nvim plugins (lazy.nvim) at the commits pinned in `nvim/lazy-lock.json`. The repo must live at `~/config`. Do NOT run it — it is only run manually.

## Binaries

`binaries/download.sh` pins tool versions via the `*_VERSION` variables at the top, verifies checksums, and extracts binaries into `binaries/<OS>/<arch>/`. Those directories are gitignored: the binaries are not committed, and `install.sh` runs the script whenever one of the expected tools is missing for the host platform.

By default the script only downloads the host platform; `--all` gets all three. Downloads happen in a scratch directory, so nothing is left behind in `binaries/` on failure. To bump a version: edit the `*_VERSION` variable, and for bat, jj and tuicr also the pinned digests in `download_platform` (they publish no checksum assets), then re-run the script.

## Scripts

`scripts/` holds the user's own commands. `.shellrc-common` appends it to `PATH`, and the pi sandbox can read it from any repository. Scripts there are portable POSIX `sh` (macOS and Linux), have no file extension and are executable.

## pi extensions

`pi/extensions/` is symlinked to `~/.pi/agent/extensions`, so every `*.ts` there is loaded globally. Nothing hot-reloads: pi has to be restarted before a change takes effect, and the extensions without their own `package.json` are typechecked by `pi/lint` (see "pi extensions lint" below).

Discovery only picks up `*.ts` and `*/index.ts`, so `pi/extensions/lib/` holds shared modules without being loaded as extensions — never add `lib/index.ts`. Since pi 1.6.0 a component's `render()` returns `readonly string[]` and pi-tui's built-in components return cached arrays, so copy the lines (`[...super.render(width)]`) before changing them.

`pi/extensions/claude-bridge/` is a fork of the MIT-licensed `@vanillagreen/pi-claude-bridge` (the `pi-claude` provider that routes turns through Claude Code via the Claude Agent SDK). It keeps the upstream layout (`src/`, `tests/`) behind a thin `index.ts`; its `README.md` lists the differences from upstream and `LICENSE` carries the upstream copyright. It has its own `package.json`; `node_modules/` is gitignored and `install.sh` runs `npm ci` there when it is missing. `npm test` and `npm run typecheck` run offline in that directory. Pi aliases `@earendil-works/*` imports to its own copies, so the pi packages in `devDependencies` only serve tests and typechecking.

`pi/extensions/i-have-adhd/` is a fork of the MIT-licensed `ayghri/i-have-adhd` (an output-style mode toggled with `/i-have-adhd`). The ruleset is `pi/skills/i-have-adhd/SKILL.md`, which the extension reads on load, so edit the rules there. Whether it starts on by default is `iHaveAdhd.alwaysOn` in `pi/settings.json`. Both directories carry the upstream `LICENSE`; the extension's `README.md` has the upstream commit and the differences. It is not listed under `packages` in `settings.json` anymore; re-adding it would register the command twice.

`pi/extensions/crit.ts` wraps the `crit` CLI (`crit_review`, `crit_comments`, `crit_comment`, `crit_status`). Story mode is authored in-session: `crit_story_prepare` runs `crit story --guide` and `crit story --prep` (prep file in the session scratch directory), and `crit_review` with a `story` object ingests it via `crit story --story-file --refresh` before the usual wait for Finish Review. `--refresh` is deliberate: without it crit keeps an existing story and skips the ingest. Bare `crit story` (the `agent_cmd` path) is not used.

The file tools (`read`, `write`, `edit`, `ls`, `find`, `grep`, `delete`) go through the path-permission engine in `pi/extensions/lib/path-permissions.ts`: the repository and the memory, skill, plan and crit directories are allowed by default (plus the session scratch directory `$(tmpdir)/pi/<last 12 characters of the session id>`, created and registered by `pi/extensions/session-scratch.ts` on `session_start`, which subagents inherit from their parent through `PI_SESSION_TEMP_DIR`), other paths prompt, and plan mode and explore mode make the repository read-only (except `.jj/working_copy/working_copy.lock` and `.jj/repo/git_import_export.lock`, which even read-only jj commands take). Rules are globs, kept separately for execution, plan and explore mode (`PathRuleStore` in `lib/agent-mode.ts`); network grants are not path rules and apply in every mode. The always tier lives in `~/.pi/agent/path-permissions.json` and the session tier in the `path-permissions` session entry, both version 3 with one sub-field per mode (`execution`, `plan`, `explore`). Manage them with `/paths [execution|plan|explore] [grants | allow <glob> | deny <glob>]` (the mode defaults to the current one); `/plan grants|allow|deny` and `/explore grants|allow|deny` manage their own mode's rules together with its tool decisions. Path prompts go through the shared `lib/permission-prompt.ts` (the same prompt flow serves every other permission prompt below). Besides the plain allow/deny options they offer "Deny with reason…" (a reason, then a duration; session and always denials keep the reason and repeat it on every later denial of the path: deny entries carry an optional `note` field, the file format stays version 3) and "Allow narrower…" (the path itself or an enclosing directory below the default grant root). Esc in a follow-up returns to the main prompt; Esc on the main prompt denies once. The sandbox's network prompt uses the same flow: its narrower option is `host:port` instead of the host on all ports, and its denial reasons live in the `denyReasons` of the `network-permissions` session entry and in `network.deniedDomainReasons` in `sandbox.json`, keyed by exact host or `host:port` (a wildcard entry written by hand in `deniedDomains` gets no reason). The unsandboxed-bash prompt and the plan/explore tool prompt use it too (unsandboxed bash offers no "always" durations, and its session denial keeps the reason in memory only). Version 2 session entries (before the per-mode split) are ignored, and a version 2 file makes every file tool fail until it is converted. `read`, `write`, and `edit` wrap Pi's stock implementations while remaining subject to the path-permission engine. `find`, `grep` and the count mode of `ls` have their own executes in `lib/search-tools.ts` (fd and rg); `find` roots path patterns at the search directory, like pi's stock `find` since 1.6.0 and `grep`'s `glob`. `read` also replaces pi's plain call line for a skill's other files (anything in a skill directory but its `SKILL.md`) with `[skill reference] <skill> › <file>`, matching pi's `[skill]` label; the skill index in `lib/skill-index.ts` is shared with the sidebar.

Explore mode (`/explore`, `--explore`, `pi/extensions/explore-mode.ts`) is plan mode without the planning tools, meant for read-only codebase exploration. `exploreMode.alwaysOn: true` in `pi/settings.json` starts every new session (launch or `/new`) in explore mode; resumed sessions keep their recorded mode, the flags still win, and sessions without a UI (subagent children, `pi -p`) and the fresh plan-handoff session ignore it. It is mutually exclusive with plan mode (toggling one leaves the other). It keeps its own memory: tool decisions in `~/.pi/agent/explore-mode.json` and the `explore-mode` session entry, path rules in the `explore` sub-field of the path rules (see above), managed with `/explore grants` and `/explore allow|deny <glob>`. Unlike plan mode, it leaves the tuicr tools ungated. Subagents enforce the path rules of the mode they were dispatched from. The mode message also tells the LLM to pass `--ignore-working-copy` to every jj command, because jj cannot snapshot a read-only working copy; the cost is that `@` can be stale until something snapshots. Both modes run on the shared engine in `pi/extensions/lib/restricted-mode.ts` (found through the runtime's event bus, so the two extensions load in any order); the mode reaches the model as an appended hidden `agent-mode-state` message, so toggling never invalidates the prompt cache.

`pi/extensions/sandbox/` overrides the built-in `bash` with one that runs every command inside `@anthropic-ai/sandbox-runtime` (pinned exactly: research preview, config format may change): Seatbelt on macOS, bubblewrap + seccomp on Linux (`sudo pacman -S bubblewrap socat ripgrep`; without them bash fails closed with an install hint; Ubuntu additionally needs `kernel.apparmor_restrict_unprivileged_userns=0` and the `bwrap-userns-restrict` AppArmor profile unloaded, because that profile strips capabilities from bwrap's children and so breaks srt's `apply-seccomp` helper). The per-command filesystem policy is derived from the path-permission engine (`currentPolicy()`), so the OS enforces the same read/write rules as the file tools. Both bash variants get the session scratch directory as `TMPDIR` (`src/scratch.ts`): a `spawnHook` sets it, and sandboxed commands also start with `export TMPDIR=…;`, because srt's `env` wrapper otherwise resets it to the shared `/tmp/claude`. On macOS a `mktemp` shim (`sandbox/bin/mktemp`, read-allowed in the sandbox) is put first on `PATH`, since macOS `mktemp` ignores `TMPDIR`; it adds `-p "$TMPDIR"` when the caller passed neither `-p` nor a template. Sandboxed commands (not unsandboxed ones or recording runs) also get a `jj` shim (`sandbox/shims/jj/jj`, `src/jj-shim.ts`, read-allowed) first on `PATH`, which runs the next `jj` on `PATH` with `--config fsmonitor.backend=none`: the sandbox denies watchman's unix socket, so a repository with `fsmonitor.backend = "watchman"` would make every snapshot report a violation, warn and fall back to a full scan, and only the command line outranks repository config. Allowing the socket instead would be a sandbox escape, because a watchman trigger runs commands outside the sandbox. srt runs each command with the first bash 5.1 or newer on `PATH` or at `/opt/homebrew/bin/bash` or `/usr/local/bin/bash` (`src/shell.ts`, resolved once at sandbox start), because macOS's `/bin/bash` 3.2 ignores `TMPDIR` for here-documents and falls back to the current directory; without one pi warns once (`brew install bash`). A denied `sh-thd-*` temp file is never prompted; the command output gets a hint instead. With `PI_SANDBOX=0` bash keeps the user's `TMPDIR`. `$HOME` is deny-read except the engine's read-allowed trees, a toolchain list (which includes `~/config/scripts`) and the `@anthropic-ai/sandbox-runtime` package itself (srt runs its vendored seccomp helper inside the sandbox, so the package must stay readable wherever `node_modules/` lives), and a built-in secret list (`.ssh`, `.aws`, `.gnupg`, `.config/gh`, `Library/Keychains`, pi auth files, ...) is denied for reads and writes even when a broad grant exists; no prompt can grant it, only a sandbox profile's `filesystem.secretRead` (below) makes listed entries readable. After a command with denied paths, they are prompted once each, whatever the exit code: "in session" and "always" answers are recorded as ordinary path rules and the agent has to rerun, while "Allow once" makes the sandbox rerun the command right away with that grant added for the rerun only (both runs' output lands in one tool result), as long as no other path of that run stayed blocked. Violations come from the extension's own collector (`src/violation-collector.ts`), not srt's store: on macOS it runs its own `log stream`, because srt's monitor keeps only the first violation of each output chunk; that stream drops the denials every macOS process hits on its own (`sysctl-read kern.iossupportversion`, `system-info vfs.disk-space` from every `statfs()`, which still succeeds, and the `diagnosticd`/`analyticsd` lookups srt's monitor drops too), and on Linux it copies every entry from srt's store before its 100-entry ring evicts it. On macOS it also takes srt's proxy (network) denials from that store, since the `log stream` only carries filesystem violations; a command's `<sandbox_violations>` block then lists network denials too, and denials that carry a user reason get an extra line repeating it. Network prompts are serialized per host: a queued prompt re-checks the session grants first, and "Allow once"/"Deny once" (or dismissing the prompt) hold until every bash command running at the time has exited, since srt does not say which command opened a connection. On Linux, read-denied paths are masked with a tmpfs, so a denied read fails with ENOENT and produces no violation record or prompt (srt 0.0.77's observer only reports write-intent syscalls); grant read access through the file tools instead. A command that exits 0 despite denials (e.g. `cmd | tail`, `cat secret 2>/dev/null || true`) is prompted too, but never rerun, so its prompts offer no "once" durations; the agent has to rerun it after a grant. Only Linux reports a denied write as discarded (its tmpfs swallowed it); macOS refuses the write and reports it as denied. Environment variables whose names look like credentials (matching `api key`, `access key`, `secret`, `token`, `password`, `credential` or `private key`, case-insensitive) are masked inside the sandbox: the process sees a sentinel, and the proxy substitutes the real value on egress to allowed domains. A tool that needs the real value locally (not through an allowed domain) will not find it; run that command with `unsandboxed: true`. Network is deny-all except the allowlist in `~/.pi/agent/sandbox.json` (optional; defaults cover GitHub, npm, crates.io and PyPI) and interactive host prompts. Subagent children get no network at all: their sandbox ignores the allowlist and session grants, denies every host and disallows unix sockets and local binding. `PI_SANDBOX=0` skips the extension and restores stock bash; that also happens silently if the extension fails to load (e.g. `node_modules/` missing), so restart pi and check that the bash tool description mentions the sandbox. Plan and explore mode leave bash ungated while the sandbox is active, since the sandbox makes the repository read-only. Subagent children of a plan- or explore-mode session get bash on the same condition: the parent admits it only while its sandbox is active, the child blocks it when its own sandbox did not load, and the child's system prompt carries the `--ignore-working-copy` note because it gets no mode message. The sandbox resets srt on `session_shutdown`: its proxy servers and the macOS `log stream` monitor otherwise keep the event loop alive, and a `pi -p` subagent child that ran bash would never exit. As a safety net, the subagent tool terminates a child that has not exited 10 s after its final `agent_end` (`subagent/exit-watchdog.ts`) and appends a note to its otherwise complete output. `bash` also takes `unsandboxed: true` for commands the sandbox itself breaks: the user confirms each one in a prompt whose preselected answer is allow, or deny in plan mode ("in session" answers hold until pi restarts, they are not persisted); subagents are refused outright, and the call line is marked `unsandboxed $`. A sandboxed call that ran with profiles shows them in front of its call line (`[bazel, node] $ …`); they travel in the result's `details.sandboxProfiles`, so a resumed session shows them too, except for calls that ended in a thrown error (abort, timeout), whose details pi drops.

The path engine also has a protected write layer: `pi/extensions/**`, `pi/skills/**` (through their `~/.pi/agent/...` symlinks), the global skill roots, `~/.pi/agent/*.json`, `~/.pi/agent/sandbox-profiles/`, `install/`, `bin/` and `npm/` prompt for writes instead of being default-allowed, for the file tools and the sandbox alike. An explicit session or always grant still works (beware: a grant of a parent such as the home directory covers them); the grant prompt warns when the granted selector also covers protected paths, since such a grant disarms the layer.

Inside the repository's `.git` and `.jj`, sandboxed writes are limited to what git and jj need to run normally (`pi/extensions/sandbox/src/vcs-policy.ts`; the allowlist comes from the git and jj command batteries in the sandbox integration tests, and a missing entry shows up as a `<sandbox_violations>` report). The layout is scanned per command, since git and jj create and remove entries all the time. macOS replaces the repository write allow with "every top-level name except `.git` and `.jj`" (generated globs, both cases of the letters excluded) plus that allowlist; this also applies when the repository root itself is granted. Linux keeps the repository writable, because srt cannot express "deny `.git`, re-allow `.git/objects`" and creating a file needs a writable parent, and denies per command every existing non-allowlisted entry plus a list of dangerous names that do not exist yet. Linux gaps: `.git/commondir` (an empty placeholder file breaks git), and `.jj/repo/config.toml` and `.jj/workspace-config.toml` in repos without config ids (the sandbox warns once; `jj config path --repo` and `jj config path --workspace` create the ids). On macOS, top-level repository names that start with a character outside `[A-Za-z0-9_@,=~#%!&-]` (after an optional `.`) are not writable from bash. `git remote add` and `jj git remote add` still need `unsandboxed: true`, because `.git/config` stays denied. `git stash` reports one denied `.git` unlink, which git ignores. On macOS a jj checkout that deletes a top-level file tries to remove the repository root itself, which Seatbelt denies; that unlink is dropped before reporting and prompting. git-lfs may write `.git/lfs`, but a sandboxed `git lfs pull` can still fail on network or credentials. `.git/objects/**` stays writable as a whole, including `objects/info/alternates`, which only adds object sources. A directory without `.git` or `.jj` keeps the plain repository allow, so `git init` works there.

Sandbox limitations (each a candidate for `unsandboxed: true`): programs that ignore proxy environment variables have no network, and ssh git remotes do not work (use https); no listening sockets unless `network.allowLocalBinding` is set in `sandbox.json` (dev servers need it); on macOS the system resolver may still answer DNS lookups initiated inside the sandbox (socket-based filtering cannot see them) while the outbound sockets themselves are blocked except the proxy; on Linux glob write allows are dropped and glob write denies widen to their base directory; `git remote add` and `git config` inside the repository fail because srt protects `.git/config` and `.git/hooks`; every other dotfile in `~/config` is still default-allowed for writes.

Sandbox profiles (`sandbox/src/profile-*.ts`, `profiles.ts`, `recorder.ts`, `recording.ts`, `trace-profile.ts`) bundle extra sandbox permissions for tools the default policy cannot run, such as bazel: read and write paths, hosts, `allowLocalBinding`, unix sockets and `PATH` directories (shims). Two fields reach past the default policy on purpose: `filesystem.secretRead` lists secret-list paths that become readable (never writable: srt applies write denies after every allow) while the profile applies (a whole secret leaves the read denies; for a path inside a secret, macOS denies the secret as the glob `<secret>/**/*`, which leaves its directory listable, because srt re-emits a literal deny after a broader allow such as a home grant and it would win; Linux keeps the literal deny, so such a partial lift is untested there), and `network.enableWeakerNetworkIsolation` (macOS) sets srt's flag of that name, which allows `com.apple.trustd.agent` so Go programs such as `gh` can verify TLS certificates; srt warns that trustd is a possible exfiltration channel. The `github` profile uses both: `gh` reads `~/.config/gh` and fetches its token from the login keychain through `/usr/bin/security`. Each lives in its own file, `~/.pi/agent/sandbox-profiles/<name>.json` (`profile-files.ts`; the file name is the profile name), and they are re-read on every bash call, so hand edits apply without a restart; a present but invalid profile file makes bash fail with its message, and so does a `profiles` key left in `sandbox.json`. A profile applies to a single bash call: one whose command matches its `triggers` (`commands` matched against the program name in command position, `patterns` as regexes over the command text; heuristics, not a shell parser) or that names it in bash's `profiles` parameter (for wrapper scripts the triggers miss). Each such call prompts through the shared permission prompt unless a session or "always" answer already decides it (preselected "Allow in session", "Allow once" in plan/explore mode). "Allow once" covers that call; "in session" and "always" answers apply the profile without asking to later calls that trigger or request it, never to other calls. A refused triggered profile leaves the command running without it; a refused requested profile, an unknown name, `profiles` with `unsandboxed`, and `profiles` in a subagent fail the call (subagents get no profiles). "Always" answers go to `profileActivation` in `sandbox.json`, never into a profile file, and `/sandbox-profile forget <name>` clears the stored and the session decision, so the profile prompts again. For that call, its paths enter the policy as once grants (in plan/explore mode profile writes that overlap the repository are dropped), its network settings (including `enableWeakerNetworkIsolation`, a top-level srt option) are merged into srt's global config through `updateConfig` while the call runs, and the shim environment (`PATH`, `PI_SANDBOX_PROFILE_FINGERPRINT`, `PI_SANDBOX_INSTANCE`, `PI_SANDBOX_STATE_DIR`) is added. `network.access` widens a profile's network on top of its listed entries: `listed` (the default) allows only `allowedDomains`, `local` also allows listening on any port and connecting to this host's loopback (`localhost`, `*.localhost`, `127.0.0.1`, `[::1]`), and `all` allows every host through the proxy as well (`*`; denied hosts still win). Neither opens unix sockets, which stay listed in `allowUnixSockets`. On Linux bwrap's network namespace has its own loopback, so `local` covers servers the command itself starts, not services on the host's loopback. srt's network settings are global, so a bash call running in parallel with a profiled call shares its network grants, `all` included. While a profile applies, the violation prompt and the network prompt offer "Add to profile <name>" (`destinations` in `lib/permission-prompt.ts`), which edits the profile and reruns the command; hostnames cannot be recorded, only prompted for. A bazel server outlives the command that started it, and its violations carry that command's tag, so a profiled command adopts the tags of the last 200 profiled commands in the violation collector. `/sandbox-profile record <name>` then `stop` records a profile on macOS: the user's own `!` commands run under a tracing Seatbelt profile (`allow default`, reporting what the normal sandbox would deny) while `log stream` collects the allow reports, and `stop` opens a collapsed draft in the editor before saving; recording runs are effectively unsandboxed. `/sandbox-profile edit|delete` manage profiles by hand. `sandbox/shims/bazel/bazel` (also linked as `bazelisk`) restarts a bazel server only when the sandbox started it and the profile fingerprint changed, never after a pi restart (it warns instead, because that server keeps the old proxy and has no network), and keeps its state under `~/.pi/agent/sandbox-state`; it finds the server through `<output_base>/server/server.pid.txt`, since `ps` fails inside the sandbox. Nested sandboxes fail on macOS (srt issue #67), so bazel's `darwin-sandbox` strategy and Swift macros do not work inside the sandbox. On Linux srt runs bwrap with `--unshare-pid --die-with-parent`, so a bazel server dies with each command and bazel restarts it every call; recording is macOS only.

`pi/extensions/cache-debug/` is always on (`PI_CACHE_DEBUG=0` turns it off) and is the first place to look when a prompt-cache miss needs explaining. It appends one JSON line per provider request to `~/.pi/agent/cache-debug/<session-id>.jsonl`: a fingerprint of the payload (a hash and size per top-level key and per array element such as each message, never content; `cache_control` markers are ignored), the response status and headers (cookies and credentials dropped), and the usage of the matching assistant message. Files untouched for 30 days are pruned at session start, and each is capped at 50 MiB. Read it with `/cache-debug [--all] [session-id]` in pi or `node pi/extensions/cache-debug/report.ts [--all] [<session-id>|<file>]`. Every miss is classified as `prefix-changed` (pi sent different content: the report names the first differing payload element and estimates its token offset), `provider-miss` (the previous payload is an exact prefix, so the miss happened on the provider's side; idle gaps over 5 minutes hint at TTL expiry) or `no-payload`. Refreshes from pi's cache warming (`cacheWarming`, `"idle"` by default since 1.5.1) are tagged through the `cache_warming_decision` event (`purpose` `"cache-warm"` on the record), reported as `cache-warm` and skipped as the comparison baseline; idle time still counts from them. Untagged refreshes in older logs show as `no-usage`. The payload is fingerprinted as `before_provider_request` sees it: the `pi-claude` bridge never calls `onPayload` and only logs usage, `before_provider_request` handlers that run after this extension are not reflected, and request headers (such as Mistral's `x-affinity`, set inside the provider) are not visible. The sandbox denies reads under `$HOME`, so agents need a read grant for `~/.pi/agent/cache-debug` to run the CLI.

`pi/extensions/default-model.ts` covers a gap in pi: when the `defaultProvider`/`defaultModel` model is missing or has no auth at startup, pi silently picks the first available model. On `session_start` (`startup` or `new`, with a UI, no conversation yet, no `--model`/`--models`, not a plan handoff) it compares the active model with the default. It refreshes the registry, switches to the default with `pi.setModel` if that now works (extension providers like `pi-claude` can register late), and warns in every case. The pure parts live in `lib/default-model.ts`.

`pi/extensions/foreign-thinking/` makes Pi 1.3.0's cross-model thinking handling configurable (Pi now drops thinking blocks from other models; 1.2 sent them as plain text). Its `context` handler rewrites assistant messages from another `provider`/`api`/`model` before the provider's `transformMessages()` sees them: `drop` removes their thinking, `text` (the default) replaces readable thinking with a `<prior_model_reasoning model="...">` text block, and `keep` gives the message the target model's identity so its thinking stays a thinking block. `keep` only applies when both sides use the same API (`claude-bridge` counts as `anthropic-messages`) and otherwise falls back to `text`; encrypted and empty thinking is always removed. Rules live under `foreignThinking` in `pi/settings.json` (`default`, plus `rules` with optional `from`/`to` globs over `provider/model`, where `*` also matches `/`; first match wins), read on `session_start`. `/foreign-thinking` shows them, `/foreign-thinking drop|text|keep` overrides every rule for the session and `reset` clears that. The `pi-claude` bridge is never a target: it has its own converter. The pure parts live in `policy.ts`.

`pi/extensions/sidebar/` draws a non-capturing overlay box in the top-right corner, made of sections (`SidebarSection` in `section.ts`). A new section is a module with a `create...Section(pi, changed)` factory, added to the `sections` array in `index.ts`. Four sections so far: the plans loaded on the current branch (first, below), the skills loaded on the current branch, split into repo skills (`sourceInfo.scope` `project`) and user skills (everything else), and the session grants (below). The skills split comes from one `createSkillsSections` factory that returns two sections sharing state, so a factory can return several sections. Detection covers a successful `read` of a skill's `SKILL.md` (matched by realpath, so calls from codemode and the `pi-claude` bridge count too) and `/skill:name`; reads through bash are not detected. Each load is recorded as a `loaded-skill` custom session entry, so the list survives resume, fork, `/tree` and compaction. Reads of other files inside a skill's directory (realpath'd, deepest skill directory wins) are listed under the skill, indented, with the path relative to that directory minus a leading `references/`, and recorded as `loaded-skill-reference` entries (`{ skill, path }`); a skill with only such reads is shown grey until its `SKILL.md` loads. The "Plans" section lists the plan files (`*.md` under `~/.pi/agent/plans/`, any working directory) touched by a successful `read`, `write` or `edit`, by filename without the `.md` extension, in first-load order. Each is recorded once as a `loaded-plan` entry (`{ path }`, the realpath), so it survives resume like the skill entries. `plan_path`, `submit_plan` and `crit_review` do not count on their own. Panel items carry a `depth` (indentation) and a `tone` (`ItemTone`), so sections never pre-format rows. The "Session grants" section lists the "in session" answers that apply right now: path rules of the active mode's store, the active plan/explore mode's tool decisions, sandbox network hosts, sandbox profile decisions and the unsandboxed-bash decision ("always" rules are not shown). The sources live in other extensions and meet on the runtime's event bus through `lib/session-grants.ts`: each registers a provider with `provideSessionGrants` and calls `announceSessionGrantsChanged` after every change (including mode switches and branch restores); the section collects on restore and on each announcement. A new source of session grants must do both, or the sidebar shows stale rows. The box is hidden while every section is empty and on terminals narrower than 100 columns. Its width follows the widest row on every render, up to a third of the terminal width; this relies on pi-tui reading the overlay options object on every frame (a `width` getter in `index.ts`). The panel is shown with `tui.showOverlay` from inside a `ui.custom` factory that calls `done()` before returning: pi counts an open `ui.custom` call as a pending prompt and emits no `ui_prompt_start` for prompts nested in it, so an overlay held open through `ui.custom` silences `notify-ask.ts`. `/sidebar [on|off]` toggles it per session (`sidebar-visibility` entry); `sidebar.enabled` in `pi/settings.json` is the persistent default, and a missing key means on. `panel.ts` takes pi-tui's width helpers as an injected `TextMeasure` and the pure modules avoid enums and parameter properties, because CI's package-less `node --test` has neither pi-tui nor type transforms.

`pi/extensions/pause/` adds `/pause`, a toggle that stops the agent at the next turn boundary that has tool results: its `turn_end` handler awaits until `/pause` runs again, a user message is queued (polled through `hasPendingMessages()`, since pi has no event for it and `input` fires before the message is queued), the run is aborted or the session shuts down. Pi stays busy while paused, so a typed message is queued as steering and goes out with the next request. A pause requested near the end of a run is dropped on `agent_settled`. The state machine lives in `gate.ts`.

`pi/extensions/footer-pickers/` makes pi's footer clickable in fullscreen mode (regular mode leaves the mouse to the terminal): the model opens a searchable model list (`lib/search-select.ts`), the thinking level a level list, and an extension status emits a click on `lib/footer-status-click.ts` with its status key, so the extension owning that status reacts; the restricted-mode engine answers for `agent-mode` with an Execute / Plan / Explore picker and shows a dim `execute` label in execution mode, and i-have-adhd toggles for `i-have-adhd` and shows a dim `○ ADHD off` label when off, so both are always clickable. Choices apply to the session only. A footer click runs its picker inside `whileAttended` (`lib/attended-prompts.ts`), and `notify-ask.ts` posts no "Waiting for your input" desktop notification for prompts opened in that window. pi's `FooterComponent` has no click hooks, so `footer-hook.ts` adds `handleMouse` to the exported `FooterComponent.prototype` and `regions.ts` maps click columns back to targets by replicating the footer layout (model and level on the right of the stats row, statuses sorted by key and joined by one space). A pi update that changes that layout makes clicks miss without an error; if pi ships its own `handleMouse`, the patch steps aside with a warning.

`submit_plan` and `crit_review` (when given a plan file inside the plans directory) commit the plan file into a repository in its plans directory (`~/.pi/agent/plans/<cwd-slug>/`), creating a colocated jj repository (or a git one when jj is missing) on first use. Commit messages are `Submit plan: <name>` and `Review plan: <name>`.

## pi extensions lint

`pi/lint/` holds ESLint (type-aware: typescript-eslint `strictTypeChecked` + `stylisticTypeChecked`, a curated set of unicorn rules, and `local/` rules in `pi/lint/rules/` for the step-down rule and separator comments) and `tsc` for the extensions without a `package.json`. It is a sibling of `pi/extensions/` on purpose: neither the package nor its `node_modules` may sit inside or above `pi/extensions/`, because pi would load an `eslint.config.ts` there as an extension and a `node_modules/` in an ancestor would change how the extensions' bare imports resolve.

The npm scripts run from `pi/` (`cd ..`): `npm run lint`, `npm run lint:prune`, `npm run fix -- <rule>...` (applies the autofixes of the named rules only), `npm test` and `npm run typecheck`. Lint needs `npm ci` in `pi/lint` and in every `pi/extensions/*/` package, because their `tsconfig.json` resolves types from their own `node_modules`.

Existing violations live in `pi/lint/eslint-suppressions.json` (ESLint bulk suppressions). New violations fail; after fixing suppressed ones, run `npm run lint:prune` and commit the file, or CI fails on the stale entries. Deliberate exceptions get an `eslint-disable-next-line <rule> -- <reason>` comment instead of a suppression.

A new extension package with its own `tsconfig.json` must be added to `parserOptions.project` in `pi/lint/eslint.config.ts`; a new entry point that needs a default export outside `extensions/*.ts` and `extensions/*/index.ts` goes into `DEFAULT_EXPORT_FILES`. typescript-eslint caps TypeScript below 6.1, so `typescript` stays on `~6.0`. The pi packages in `pi/lint` and in every extension package's `devDependencies` are pinned exactly to the pi release that runs (`~/.pi/agent/install/releases/<version>`); bump them together after a pi update, since CI typechecks against them.

## pi skills

`pi/skills/` is symlinked to `~/.pi/agent/skills`, pi's global skill root. Each skill is `pi/skills/<name>/SKILL.md`. A skill meant for Claude Code as well stays there, and `install.sh` links its directory into `~/.claude/skills/`; add its name to the `for skill in ...` loop there (see `code-style`).

## pi themes

`pi/themes/` is symlinked to `~/.pi/agent/themes`, pi's global theme directory; pi loads every `*.json` there, and the active theme hot-reloads from it. `gruvbox-dark.json` (the `theme` in `settings.json`) is inlined from the MIT-licensed `@firstpick/pi-themes-bundle`; `pi/themes/README.md` lists the source and the differences, and `LICENSE` carries the upstream copyright. Validate theme files against `schemas/theme.schema.json` of the installed pi package.

## pi packages

`pi/npm/` holds `package.json` and `package-lock.json` for the npm packages in `settings.json`. `install.sh` symlinks both into `~/.pi/agent/npm` (pi's npm install root, whose own `.gitignore` ignores everything else) and runs `npm ci` there when `node_modules` is missing. `pi update --extensions` runs `npm install <name>@latest` there, which rewrites the repo files through the symlinks (npm writes through them, verified), so review and commit the diff after each update. Git packages have no lockfile: their commit is only recorded in the checkout under `~/.pi/agent/git/`.

## CI

`.github/workflows/` has six workflows with 9 independent jobs in total. GitHub's `paths:` filter works per workflow, so jobs that share inputs live in one workflow, each with a `push` (to `main`) and `pull_request` `paths:` filter (shared through a YAML anchor) that always includes the workflow's own file. `workflow_dispatch` and `schedule` ignore `paths:` and always run every job. `nvim`, `vim`, `extensions` and `binaries` also run weekly, to catch upstream breakage that a push wouldn't (`stable` nvim, vim-plug plugins, which have no lockfile, `latest` node, dead release URLs); `shellcheck` and `actionlint` don't, since their tools are pinned.

Known gap: the `shellcheck` paths cover `.sh` files plus the extensionless shell files by name (`.ansi-colors`, `.shellrc-common`, `.git_template/hooks/`, `scripts/`); a new extensionless shell script elsewhere won't trigger it on its own PR, so add its path to `shellcheck.yml`.

`shellcheck.yml` (paths: shell files and `.github/scripts/shellcheck.sh`), `actionlint.yml` (paths: `.github/workflows/**`), `nvim.yml` (paths: `nvim/**`, `nvim-check.lua`), `vim.yml` (paths: `.vimrc`, `.vim/**`), `extensions.yml` (paths: `pi/extensions/**` and `pi/lint/**`, because `sandbox` imports from `pi/extensions/lib/`) and `binaries.yml` (paths: `binaries/download.sh`):

- **shellcheck**: lints shell scripts. `.github/scripts/shellcheck.sh` auto-discovers every tracked file with a shell shebang or `.sh` suffix and runs the same way locally.
- **actionlint**: lints the workflow files.
- **stylua**: checks formatting of `nvim/`.
- **node**: `npm ci` + `npm test` + `npm run typecheck` in every `pi/extensions/*/` directory that has a `package.json` (discovered automatically, so new packages need no workflow change but must define both scripts), plus `node --test pi/extensions/*/*.test.ts` for the package-less directories (`lib`, `subagent`, `cache-debug`, `foreign-thinking`, `sidebar`, `pause`, `footer-pickers`; the `lib` tests need `fd` on `PATH`). Matrixed on the `engines` floor (22.19.0) and `latest`.
- **lint**: `npm ci` in `pi/lint` and in every extension package, then `npm run typecheck`, `npm test` and `npm run lint` in `pi/lint` on node 22.19.0.
- **nvim**: installs plugins from `nvim/lazy-lock.json` via `Lazy! restore`, then runs `.github/scripts/nvim-check.lua` headless, which force-loads every plugin and fails on any config error. Matrixed on `v0.12.0` (the floor, since `nvim-treesitter` on `main` requires it) and `stable`. `nvim-check.lua` runs the same way locally: `nvim --headless --cmd "luafile .github/scripts/nvim-check.lua"`.
- **vim**: installs plugins with vim-plug and checks for startup errors. vim-plug has no lockfile, so this always tests upstream HEAD — the weekly run is what surfaces breakage here.
- **downloads**: runs `binaries/download.sh` and smoke-tests every binary, natively on all three supported platforms (`ubuntu-26.04`, `ubuntu-26.04-arm`, `macos-26`).
- **sandbox**: runs `npm run test:int` in `pi/extensions/sandbox/` natively on `ubuntu-26.04` (with bubblewrap installed, the AppArmor userns sysctl lifted and Ubuntu's `bwrap-userns-restrict` profile unloaded) and `macos-26`; it drives the real sandbox, unlike the unit tests in the node job.

All actions are pinned to version tags; Dependabot (`.github/dependabot.yml`) keeps them current.
